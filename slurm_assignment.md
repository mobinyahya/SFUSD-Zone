I want to deploy this code on a server that uses slurm. Specifically I want the assignment and benchmark packages to all have the option to use sbatch for running jobs. 

First we will support the benchmark/ package. Generating zones and calculating metrics should be seperated into two phases (ignore matching and choice metrics for now. just throw an error if matching or choice metrics is true). You might need a script that turns benchmark configs into some bash script that uses sbatch and has all the correct jobs ids. For the optimization phase, each optimization run in the sweep should be its own job with a number of workers corresponding to the number of workers in the config. The second phase is the metric evaluation phase. After each optimization job is complete, you should add an evaluation job that just evaluates and calculates metrics for that zoning. It should append its results to an aggregate summary csv and stages.csv so that once all workers are complete the summary and stages csv will be filled. This will always use just one cpu core. For slurm runs ignore capacity, max_workers, and max_tasks_per_worker params. For recursive and iterative choice strategies, you do not need to create multiple jobs, jsut keep everything in the same job. 


Next we will support the assignment/ package. This will have a few phases. Again, given some config path, split the tasks into jobs so that we have 1 job per subconfig and iteration pair. So if we consider assignment/configs/kumar.config.yaml, you would have a job for every iteration of each policy sub config. Then if export-aggregate-metrics: true you will add another job that requires every iteration for a particular subconfig to be complete. Once it is complete, you should append metrics to the metrics csvs in the aggregate metrics directory. If export-local-metrics:true also append program-level output and metrics by zip code and attendance area. All of these jobs will use one cpu core, there will just be a lot of jobs


When possible, try to avoid too much data reloading. There should be separate scripts for benchmark and assignment. NOTE THAT THIS COMPUTER DOES NOT USE SLURM. You will have to design for a system that eventually does, and cannot test your implementation through directly using slurm and will have to design dry tests with configs.
